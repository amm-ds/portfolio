# Architecture proposal: RAG grounding verifier challenger (project 01)

Date: 2026-11-19
Designer: Claude Code
Status: draft
Source design brief: `collaboration/designs/20261119-rag-verifier-challenger/01-design-brief.md`

## Decision

Add an offline verifier challenger harness to project 01 that scores the committed 194-claim calibration set with grounding-trained verifiers, using a fixed dev/test split and pre-registered gates. Nothing in the agent, the verify loop, or the app changes in this round. The challenger is a measurement, not a production swap.

Reason: the project's weakest measured number is the verifier's false acceptance of unsupported claims. Offline scoring on labeled claims is the only way to test a new verifier without hosted spend, and the existing committed judges give a same-label baseline.

## System shape

```text
claims.jsonl (194; committed, fixed split by seed)
  → challenger adapter (one class per verifier; common interface: score(claim, evidence) → p_supported)
  → threshold chosen on DEV only
  → TEST scoring; FA(strict), false rejection, Wilson 95%
  → reports/verifier_challenger/{metrics.json, predictions.jsonl, report.md}
```

Phase 2a adds one step:

```text
committed sealed claims (citation_records_heldout.json, sealed_v2 traces)
  → same adapter, same frozen threshold
  → reports/verifier_challenger_replay/{metrics.json, report.md}
     (keep/drop counts, ALCE-style citation precision and recall)
```

## Contracts and data ownership

- Adapter interface: `score(claim: str, evidence: str) -> float` in `[0, 1]`, deterministic on CPU, no network after the checkpoint is cached.
- Threshold: a single float chosen on DEV by maximizing a fixed rule (see gate), stored in the metrics file. It is not tuned after TEST is seen.
- Split: `dev`/`test` assignment is a seeded stratified split (label-balanced, seed 42, matching the project's bootstrap seed). The split file is committed before scoring.
- Baselines: hosted qwen3:4b and local qwen2.5:3b decisions are read from their committed predictions/results files. The committed hosted aggregate (0.4536) is not used, per `judge_calibration_report.json`.
- Generated files: everything under `reports/verifier_challenger*/` is generated by one script from committed inputs. No hand edits.
- New files only. No existing report, label set, or copy is modified.

## Alternatives considered

| Alternative | Why rejected |
|---|---|
| Re-prompt the existing LLM judge with a different prompt | Tried in R8 (strict entailment prompt); traded FA for over-abstention |
| Fine-tune a new verifier on project data | No hosted spend allowed in this round; 194 labels too few to train from scratch; would make the test set a training leak risk |
| Score on all 194 claims with no split | Threshold would be chosen on the same claims that report the result; biased |
| Replace the production verify loop now | Changes the answer path before any offline evidence exists |

## Failure modes and limits

| Failure or limit | Detection | Behavior |
|---|---|---|
| Checkpoint download blocked or license disallows use | Download step error; license check in handoff | Fall back to the named second candidate (NLI cross-encoder) after owner approval; else stop and report |
| Scores unstable across CPU runs | Re-score twice; compare flip rate | Report flip rate; if above 5%, do not gate |
| Claims longer than model context | Token-length check before scoring | Truncate evidence with a logged count; never silently drop claims |
| Split leaks into threshold choice | Threshold code reads DEV rows only (asserted in test) | Test fails; no result published |
| n = 194 gives wide intervals | Wilson intervals reported | Result is a directional finding, not a certified rate |
| Challenger wins on the 194 set but not end to end | Phase 2b (owner-approved) | Copy does not change on Phase 1 alone |

## Migration and rollout

1. Owner approves the design and the checkpoint download, naming source and size.
2. Kimi commits the split file, then the adapter and tests, then runs Phase 1 once.
3. Gate result is reported to the owner. Only if it passes: Phase 2a replay, offline.
4. Owner decides on Phase 2b (new cap) and on any copy change. No copy changes before that.

## Observability and verification

- Metrics file: threshold, dev and test counts, FA(strict) and Wilson 95%, false rejection and Wilson 95%, flip rate over two CPU runs, runtime, checkpoint hash.
- Predictions file: one row per claim with split, label, score, decision.
- Tests: split is seeded and disjoint; threshold function reads DEV only; adapter returns scores in `[0, 1]`; Wilson function matches the project's existing helper on a known case.
- Gates: `uv run pytest -q projects/01-rag-agent`, `ruff check`, `ruff format --check`, `mypy` on new code, `uv run python scripts/check_headline_numbers.py`, `uv run python scripts/check_docs.py`.

## Rollback

- Safe rollback point: the commit before the challenger harness. Deleting the new report folders and the harness module reverts everything.
- Data or state that rollback does not undo: the downloaded checkpoint in the local model cache. It is outside the repository and is safe to delete.
